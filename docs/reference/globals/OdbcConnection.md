# OdbcConnection

What [`Database.Odbc`](Database.md) answers: a connection through an ODBC
driver to whatever server the machine has one for -- SQL Server, MySQL/MariaDB,
PostgreSQL, Firebird, an Access file. It **is** a `Connection`, so
`Table(name, RecordClass)` and `Cursor(sql, …)` work on it as they do on
sqlite's.

```js
const db = Database.Odbc("Driver={ODBC Driver 18 for SQL Server};" +
                         "Server=erp.internal;Database=Ventas;Encrypt=yes",
                         { User: "facturacion",
                           Password: Environment.Get("ERP_DB_PASSWORD"),
                           Timeout: 10000, StatementTimeout: 30000 });
const db2 = Database.Odbc("DSN=Ventas");      // configured by the administrator

db.Dbms                                        // "Microsoft SQL Server"
db.Query("SELECT id, total FROM invoices WHERE client = ?", [42]);
```

The connection string is **the driver's**, passed as written: a `DSN=` or a
`Driver={…};…`. The options are the four every driver shares -- `User`,
`Password`, `Timeout` and `StatementTimeout`, in milliseconds -- and any
other key is refused, since it belongs in the string. A driver never opens a
dialog. A failure throws with the driver's message, the SQLSTATE in `Code`,
the engine's number in `Native` and further records in `Details`; **the
message comes in the desktop's language**, so a program branches on `Code`.

## Every member

| | |
|---|---|
| `Query(sql, [params])` | the rows of the first result that has any, as **plain objects**; `[]` for a statement with none. Values are bound to `?`, never pasted: text, a number, a boolean, a `Decimal`, a `Bytes` or null |
| `Execute(sql, [params])` | **one** statement, answering `{ Changes }` -- the rows it touched, `-1` when the driver cannot say. An `UPDATE` that matched nothing is `0`, not an error |
| `Script(sql)` | several statements and **no parameters**, as the driver runs a batch: psqlODBC takes one, sqliteodbc refuses a second statement |
| `Each(sql, [params], fn)` | the rows **one at a time**: `fn(row)` for each, never an array of all of them. `fn` returning `false` stops; the answer is how many rows were handed over. `Close()` is refused while it reads |
| `Transaction(fn)` | everything in `fn` or nothing, and what `fn` returns. **Nests**, through savepoints in the engine's spelling. A throw rolls back and is rethrown |
| `Columns(table)` | what is really in the table, from the driver's catalogue: `Type` is the engine's own name for it, `Key` the position in the primary key (0 for none); `[]` when there is no such table |
| `Tables` (ro) | the tables and views, ordered, each name once whatever schema it is in; the engine's own schemas are left out |
| `Dialect` (ro) | what differs per engine, from `Dbms`: `Placeholder`, `Quote`, `NewKey` (`"Returning"`, `"Output"`, `"Select"` with `KeyQuery`, or `"None"`), `Page`, `Decimal`, `Types` and `AutoKey` -- what `Table`, `Cursor` and `Model` read instead of assuming sqlite |
| `Dbms` (ro) | the engine, as the driver names it: `"PostgreSQL"`, `"SQLite"`, `"Microsoft SQL Server"`. Still answers after `Close` |
| `DbmsVersion` (ro) | the engine's version, as the driver writes it |
| `Driver` (ro) | the driver's own file name: `"psqlodbcw.so"`, `"msodbcsql18.dll"` |
| `Open` (ro) | whether it still is |
| `Close()` | let it go; twice is not an error |

## Reading

Every value is bound to a `?`, never pasted, and a column comes back by the
type the driver describes: a boolean, a number, a `NUMERIC` as its exact text
(never through a double, whatever the desktop's decimal comma), a date as
`YYYY-MM-DD`, a timestamp as `YYYY-MM-DDTHH:MM:SS` with its fraction when it
has one, binary as `Bytes`, the rest as text.

## Writing

`Execute` is one statement; a key generated by the engine comes back through
`Table.Insert`, the engine's way. A `Transaction` is ODBC's own at the outside
and a savepoint inside.

## What each engine answers

`Dialect` comes from `Dbms`, because ODBC makes the connection alike and not
the SQL:

| `Dbms` | a new key | a cursor | `Model` creates a table |
|---|---|---|---|
| `PostgreSQL` | `RETURNING` | `LIMIT`/`OFFSET` | yes |
| `SQLite` | `last_insert_rowid()` | `LIMIT`/`OFFSET` | yes |
| `Microsoft SQL Server` | `OUTPUT INSERTED` | refused | refused |
| `MySQL`, `MariaDB` | `LAST_INSERT_ID()` | `LIMIT`/`OFFSET` | refused |
| any other | refused: give the record its key | refused | refused |

Run against psqlODBC and sqliteodbc; the SQL Server and MySQL rows come from
their drivers' documentation. Where `Model` is refused, create the table
yourself and the `Model` uses it.

## What the drivers do

- **The drivers are the machine's**, installed and configured with
  `odbcinst` (Linux, macOS: unixODBC) or the ODBC administrator (Windows). A
  Flatpak sees none of the host's.
- **psqlODBC**: `NUMERIC` is exact, a `boolean` is a boolean, a
  `timestamptz` loses its offset (it is converted to the session's zone), and
  an error caught inside a `Transaction` undoes only its own statement.
- **sqliteodbc** answers every error as `HY000` and refuses a second
  statement in `Script`; `Database.Sqlite` is the way to a sqlite file.
- `Script` runs a batch the driver's way; psqlODBC undoes the whole batch when
  one statement fails.
- Optional at build time on Linux and macOS; without unixODBC
  `Database.Odbc` says which package is missing. Always there on Windows.
